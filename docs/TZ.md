# Zabbix Action Audit — техническое задание и архитектура

Статус: **согласовано 2026-10-12** (оба режима, HTML, интеграционные тесты на стенде), реализовано.
Поддерживаемые версии Zabbix: **6.0 LTS – 7.4** (проверено на 7.4.9 и 6.0.48).

---

## 1. Цель

Консольное Python-приложение, которое строит отчёт по **действиям триггеров** (`action.get`, `eventsource=0`) и для каждого действия отвечает на вопросы:

1. **Под какие проблемы попадает действие** — какие триггеры (и их текущие проблемы) удовлетворяют условиям действия.
2. **Дойдёт ли уведомление до каждого получателя** по каждой из этих проблем, а если нет — почему:
   - есть ли у пользователя доступ к хостам (хостам из условий действия и хостам проблем);
   - есть ли у пользователя медиа нужного типа (медиатип из операции);
   - разрешает ли медиа пользователя отправку для уровня важности проблемы.


## 2. Область применения

### Входит
- Действия с `eventsource=0` (триггеры), включённые и выключенные (выключенные — помечаются отдельно, опцией можно исключить).
- Операции всех трёх видов: `operations`, `recovery_operations`, `update_operations`.
- Тип операции «Отправить сообщение» (`operationtype=0`) — полный аудит получателей.
- «Уведомить всех участников» (`11`, `12`) — помечается как информационное, получатели не раскрываются (они определяются в runtime).
- «Удалённая команда» (`1`) — только перечисляется в отчёте (без аудита получателей).

### Не входит (v1)
- Действия обнаружения, авторегистрации, внутренние, сервисные.
- Проверка доставки на транспортном уровне (реальные отправки, валидность токенов Telegram и т.п.).
- Изменение конфигурации Zabbix — приложение **только читает** (кроме интеграционных тестов, см. §8).

## 3. Термины

| Термин | Значение |
|---|---|
| Кандидат | Триггер (статический режим) или активная проблема (режим `active`), проверяемые на соответствие условиям действия |
| Получатель | Пользователь из `opmessage_usr` либо участник группы из `opmessage_grp` |
| Находка (finding) | Результат проверки с кодом, уровнем (`OK`/`INFO`/`WARN`/`FAIL`) и пояснением |

## 4. Функциональные требования

### FR-1. Подключение
- URL и API-токен читаются из `secrets.txt` (формат `Zabbix_url: …` / `Zabbix token: …`), с возможностью переопределения через переменные окружения `ZABBIX_URL`, `ZABBIX_TOKEN` и аргументы CLI.
- Авторизация — `Authorization: Bearer <token>`. Токен в логах и отчётах не выводится.
- Проверка TLS: по умолчанию системные CA; `--no-verify-ssl` / `ZABBIX_VERIFY_SSL=false` / `Zabbix verify ssl: false` — отключить (одно предупреждение в лог вместо `InsecureRequestWarning` на каждый запрос); `--ca-bundle FILE` или путь в тех же переменной/строке — свой CA.
- Пользователь токена должен быть Super admin (иначе API вернёт неполные данные) — проверяется при старте, иначе предупреждение.

### FR-2. Определение проблем, под которые попадает действие
Два режима (выбираются флагом `--mode`, по умолчанию оба):
- **`potential`** — все включённые триггеры на включённых хостах (не шаблонах). Отвечает на вопрос «что *может* прийти».
- **`active`** — текущие проблемы (`problem.get`). Отвечает на вопрос «что *сейчас* должно было прийти».

Поддерживаемые условия (`conditiontype`) и операторы:

| Код | Условие | Операторы | Как вычисляется |
|---|---|---|---|
| 0 | Группа узлов | `=`, `<>` | группы хоста триггера, **включая вложенные** (как в Zabbix) |
| 1 | Узел | `=`, `<>` | хосты триггера |
| 2 | Триггер | `=`, `<>` | triggerid |
| 3 | Имя события | contains / not contains | `event_name` триггера, иначе `description`; `{HOST.*}` и пользовательские макросы раскрываются (хост → шаблоны → глобальные), прочие макросы → `UNKNOWN`, если от них зависит результат |
| 4 | Важность триггера | `=`, `<>`, `>=`, `<=` | priority |
| 6 | Период времени | in / not in | **не вычисляется статически** → результат `UNKNOWN` (в `active` — по времени проблемы) |
| 13 | Шаблон | `=`, `<>` | цепочка `templateid` триггера (с учётом вложенных шаблонов) |
| 16 | Проблема подавлена | Yes / No | в `potential` → `UNKNOWN`; в `active` — по полю `suppressed` |
| 25 | Тег события | `=`, `<>`, contains, not contains | теги события = теги триггера + хоста + шаблонов |
| 26 | Значение тега | те же | то же |

- Тип вычисления (`evaltype`): 0 «И/ИЛИ» (одинаковые типы — ИЛИ, разные — И), 1 «И», 2 «ИЛИ», 3 пользовательская формула.
- Логика **трёхзначная**: `MATCH` / `NO_MATCH` / `UNKNOWN`. Кандидаты с `UNKNOWN` выводятся отдельно с указанием условия, из-за которого результат не определён.
- Макросы в значениях тегов (`{HOST.NAME}` и т.п.) раскрываются по возможности; если раскрыть нельзя — `UNKNOWN` с пометкой.
- Ссылки в условиях на несуществующие объекты (удалённый триггер/хост/группа) → `WARN`.

### FR-3. Раскрытие получателей
- Для каждой операции «отправить сообщение»: пользователи + члены групп; дубли сводятся, сохраняется источник («напрямую» / «через группу X»).
- Учитываются `esc_step_from/to` и `opconditions` (подтверждено/нет) — выводятся в отчёте как контекст операции.
- Пустой список получателей → `FAIL`.

### FR-4. Проверки получателя (по каждой паре «получатель × проблема»)

| Код | Уровень | Проверка |
|---|---|---|
| `USER_DISABLED` | FAIL | пользователь состоит в группе с `users_status=1` |
| `USER_NO_HOST_ACCESS` | FAIL | у пользователя нет прав минимум «Чтение» на хост проблемы (не Super admin) |
| `USER_TAG_FILTER_BLOCKS` | FAIL | права есть, но tag-фильтры групп пользователя скрывают эту проблему |
| `USER_NO_MEDIA` | FAIL | у пользователя нет ни одного медиа (при `mediatypeid=0`) или нет медиа указанного типа |
| `MEDIA_DISABLED` | FAIL | медиа пользователя нужного типа есть, но выключено (`active=1`) |
| `MEDIATYPE_DISABLED` | FAIL | сам медиатип выключен (`status=1`) |
| `MEDIA_SEVERITY_EXCLUDED` | FAIL | маска важности медиа не содержит важность проблемы |
| `MEDIA_EMPTY_SENDTO` | WARN | пустой адрес отправки |
| `MEDIATYPE_NO_MESSAGE_TEMPLATE` | WARN | в типе медиа нет шаблона сообщения для вида операции (проблема/восстановление/обновление) при «сообщении по умолчанию» |
| `MEDIA_PERIOD_EXCLUDED` | WARN | (режим active) проблема возникла вне периода активности медиа |
| `MEDIA_PERIOD_LIMITED` | INFO | период активности медиа не 24/7 — указывается расписание |
| `OK` | OK | все проверки пройдены хотя бы для одного медиа |

Правила вычисления прав (как в Zabbix 7.x):
- Super admin (`role.type=3`) — полный доступ, tag-фильтры не применяются.
- Право на группу узлов по группам пользователя: если хотя бы одна группа даёт **Запрет** — запрет; иначе максимальное право.
- Право на хост: по всем его группам узлов; запрет на любую — запрет; иначе максимум.
- Tag-фильтры: применяются только для групп пользователя, где на эту группу узлов заданы фильтры; если какая-то группа пользователя даёт доступ к группе узлов **без** фильтров — фильтров нет.
- Правильность модели прав проверяется интеграционным тестом-оракулом: под тестовыми пользователями выполняется `user.login` + `host.get`/`problem.get` и результат сравнивается с вычисленным.

### FR-5. Проверки на уровне действия
| Код | Уровень | Проверка |
|---|---|---|
| `ACTION_DISABLED` | INFO | действие выключено |
| `ACTION_MATCHES_NOTHING` | WARN | ни один кандидат не подходит под условия |
| `ACTION_ONLY_UNDECIDED` | WARN | определённых совпадений нет, но есть кандидаты «не определено» |
| `ACTION_NO_SEND_OPS` | INFO | нет операций отправки сообщений |
| `COND_HOST_NOT_ACCESSIBLE` | WARN | хост/группа из условий действия недоступны какому-то получателю (даже без учёта проблем) |
| `COND_SEVERITY_VS_MEDIA` | WARN | важности, допускаемые условием действия, не покрываются медиа получателя ни для одной важности |
| `COND_REF_MISSING` | WARN | ссылка на удалённый объект |
| `ACTION_PAUSE_SUPPRESSED` | INFO | действие ставит эскалацию на паузу в обслуживании |
| `ACTION_COND_NOT_SUPPRESSED` | WARN | условие «Проблема подавлена: нет» — проблемы, начавшиеся в обслуживании, теряются; рекомендуется пауза в операциях |

### FR-6. Отчёт
- Форматы: `text` (консоль, сводка), `json` (машиночитаемый, полный), `html` (самодостаточный файл, раскрывающиеся блоки по действиям → операциям → получателям → проблемам, фильтр по уровню).
- Сводка: по каждому действию — число подходящих проблем, число пар «получатель × проблема» в разрезе OK/WARN/FAIL, топ причин.
- Чтобы не раздувать отчёт при тысячах триггеров, одинаковые результаты группируются: «user22 → 1 240 проблем: FAIL `USER_NO_HOST_ACCESS`» с раскрываемым списком.
- Опционально (`--uncovered`): триггеры, не подпадающие **ни под одно** включённое действие с отправкой сообщений.
- Код возврата: `0` — нет FAIL, `1` — есть FAIL, `2` — ошибка выполнения (удобно для CI/cron).

### FR-7. CLI
```
zabbix-action-audit [--secrets secrets.txt] [--url URL] [--token TOKEN]
                    [--mode potential|active|both] [--action ID|NAME ...]
                    [--skip-disabled] [--uncovered] [--tz ZONE]
                    [--format text|json|html] [--output FILE]
                    [--dump-snapshot FILE | --from-snapshot FILE]
                    [--no-verify-ssl | --ca-bundle FILE] [-v]
```
`--dump-snapshot` / `--from-snapshot` — сохранить/использовать выгрузку API, чтобы проводить аудит офлайн и воспроизводить баги.

## 5. Нефункциональные требования
- Python ≥ 3.10; зависимости — минимальные: `requests`, `jinja2`. Без pyzabbix — тонкий собственный клиент.
- Производительность: все данные выгружаются пакетно (≈10 запросов на весь аудит, без N+1), вычисления в памяти. Цель — 50 000 триггеров / 1 000 пользователей за < 1 мин.
- Только чтение API.
- Типизация (`dataclasses`, type hints), `ruff` + `mypy` чистые.

## 6. Архитектура

```
             ┌──────────┐   JSON-RPC    ┌────────────┐
 secrets ──▶ │  config  │──▶ api.client ─▶│ Zabbix API │
             └──────────┘               └────────────┘
                                │
                                ▼
                         loader.Snapshot  ◀──▶  snapshot.json (dump/load)
                                │  (иммутабельная модель всех данных)
         ┌──────────────────────┼─────────────────────┐
         ▼                      ▼                     ▼
  conditions.Evaluator   permissions.Resolver   media.Checker
   (действие × кандидат)  (пользователь × хост/  (пользователь ×
    → MATCH/NO/UNKNOWN     теги) → доступ         медиатип × важность)
         └──────────────────────┼─────────────────────┘

                                ▼

```

### Выгружаемые данные (Snapshot)
| API | Что берём |
|---|---|
| `action.get` (eventsource=0) | filter, operations, recovery/update operations |
| `trigger.get` | priority, status, event_name, description (expanded), tags, hosts, templateid, functions не нужны |
| `problem.get` (режим active) | objectid, severity, tags, suppressed, clock |
| `host.get` | status, hostgroups, tags + inheritedTags, parentTemplates |
| `template.get` | parentTemplates (для вложенности) |
| `hostgroup.get` | имена (для вложенности `A/B`) |
| `user.get` | role.type, medias, usrgrps |
| `usergroup.get` | users_status, hostgroup_rights, tag_filters, users |
| `mediatype.get` | status, type, name |

### Ключевые решения
1. **Snapshot отделён от логики** — вся бизнес-логика тестируется юнит-тестами без Zabbix, а интеграционные тесты проверяют выгрузку и соответствие реальному поведению.
2. **Трёхзначная логика** вместо ложных «попадает/не попадает» для условий, зависящих от времени и подавления.
3. **Права вычисляются локально**, но валидируются оракулом (логин тестовыми пользователями) — это главный риск корректности.
4. **Группировка findings** — отчёт остаётся читаемым при тысячах триггеров.

## 6a. Совместимость с Zabbix 6.0 LTS

Различия API проверены на живых 6.0.48 и 7.4.9 и изолированы в `api.py` / `loader.py` (остальной код работает с нормализованной выгрузкой):

| Что | 6.0 / 6.2 | 6.4 / 7.x |
|---|---|---|
| Авторизация | поле `auth` в теле запроса | заголовок `Authorization: Bearer` (поле `auth` в 7.2+ запрещено) |
| Группы узлов хоста | `selectGroups` → `groups` | `selectHostGroups` → `hostgroups` |
| Права групп пользователей | `selectRights` → `rights` | `selectHostGroupRights` → `hostgroup_rights` |
| Кто владелец токена | `user.checkAuthentication {sessionid}` | `user.checkAuthentication {token}` |
| Группы шаблонов | общие с группами узлов | отдельные `templategroup` (только в тестах) |

6.0 молча игнорирует неизвестные `select*`-параметры, поэтому запрос строится по версии, а не «с запасом».

## 7. Риски и допущения
- Точная семантика объединения прав/tag-фильтров при нескольких группах пользователя в разных версиях Zabbix отличалась → закрывается тестом-оракулом.
- Раскрытие макросов в именах событий/тегах — частичное (`expandDescription` только для имени; пользовательские макросы в тегах — по возможности).
- Макросы в периоде медиа (`{$WORKTIME}`) — раскрываются через `usermacro.get` (глобальные), иначе INFO «не удалось вычислить».

## 8. Тестирование
- **Юнит-тесты** (pytest): каждый тип условия × оператор × evaltype, формулы, права (deny-приоритет, вложенные группы, tag-фильтры), медиа (маска важности, выключенные медиа/медиатипы, `mediatypeid=0`).
- **Интеграционные** (на `192.168.88.40`): фикстура создаёт объекты с префиксом `zaa-test-` — группы узлов, хосты, триггеры (на item типа trapper), группы пользователей с разными правами/tag-фильтрами, пользователей с разными медиа, действия — запускает аудит и сверяет ожидаемые коды находок. После теста всё удаляется (в т.ч. при падении). Существующие объекты стенда не изменяются.
- Тест-оракул прав: тестовые пользователи логинятся и сравнивается видимость хостов/проблем с вычисленной.
- Запуск: `pytest` (только юнит), `pytest -m integration` (стенд).

## 9. Этапы
1. Каркас, клиент API, загрузка Snapshot, dump/load — + интеграционный тест выгрузки.
2. Вычислитель условий + юнит-тесты.
3. Права и tag-фильтры + оракул.
4. Проверки медиа, auditor, группировка.
5. Отчёты text/json/html, CLI, коды возврата.
6. Интеграционный end-to-end, README.

## 10. Решения
1. Оба режима, по умолчанию `both`.
2. Основной формат — HTML; также text и JSON.
3. Интеграционные тесты создают/удаляют `zaa-test-*` объекты; тестовые действия выключены. Реальные проблемы генерируются только если ни одно существующее включённое действие стенда не подпадает под тестовые триггеры (проверяется самим аудитором) — на 192.168.88.40 это действие «all problems to tg», поэтому там тесты режима active пропускаются и выполняются на стенде 6.0 в Docker.
4. `--uncovered` реализован (по умолчанию выключен).
